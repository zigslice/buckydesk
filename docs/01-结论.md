# 结论

BuckyOS 是一套以 Zone 为单位的个人云操作系统。一台机器上的 BuckyOS 是这个 Zone 里的一个节点，通常还是唯一的 OOD（Owner Online Device）。它的主链路是：身份与 ZoneBootConfig、`system-config`、scheduler、`node-daemon`、`cyfs-gateway`，再加上容器里的 App 和 Agent。

这个模型默认网络不稳定、身份必须可验证、服务可以多机部署。它适合家庭服务器和开发机，不适合作为「任意一台 Windows/Mac 装完就能用」的桌面软件。BuckyDesk 要做的是后一种产品：用户安装之后，本机成为一台已经激活的单 OOD Zone，并有一个窗口能打开系统桌面。

上游已经有桌面发行的零件，缺的是把零件接成一条不要求用户懂 Zone 的路径。

## 上游已经有的

- **运行时。** `node-daemon` 拉起内核服务，按 `node_config` 收敛本机；scheduler 把 Zone 状态写成运行意图；`cyfs-gateway` 提供 `127.0.0.1:3180` 的本机入口。
- **Web 桌面。** `src/frame/desktop` 是 React 控制面板，构建后装到 `bin/control-panel/web/`。窗口、任务栏、设置、AI Center、文件和消息都在这个 Web UI 里，不在原生壳里。
- **身份壳。** `BuckyOSApp` 是 Tauri 应用，目标平台包括桌面和移动端。它管理本机助记词 DID，向激活页注入 `window.BuckyApi`，并能打开局域网扫描到的或用户手动填入的 3182 激活页。现行需求把它限制在「身份入口 + WebView 容器」：不监管 `node-daemon`，不安装 Zone 内应用。
- **安装包骨架。** `src/bucky_project.yaml` 把 macOS/Windows 发行拆成两个组件：桌面 App（`/Applications/BuckyOS.app` 或 `buckyosapp.exe`）和桌面服务（`/opt/buckyos` 或 `C:\BuckyOS`）。打包脚本在 `buckyos-pack-installer`。
- **一条可离线的首次激活。** websdk 的 `buckyos provision activate` 能在本机、无网络、无 SN/BNS 的前提下，为已安装根目录生成单 OOD、`did:web` 的身份文件。它不启动服务。
- **一条面向注册用户的网页激活。** 未激活时 `node_daemon --enable_active` 在 3182 提供向导。成功后进程大约 2 秒后退出，等待外部监管进程再把它拉起来。

## 上游没有替桌面用户做完的

这些不是「缺一个按钮」，而是桌面产品必须自己收口的运行条件。

1. **第一次打开就要做身份决策。** 网页向导默认要 SN 账号、邀请码和网关拓扑（SN 中转、端口转发或公网 IP）。只有「固定公网 IP + 自有域名」会跳过 SN。普通笔记本用户没有这条路径。`provision` 可以本地生成身份，但要求调用方提供域名、管理员密码和 Owner 私钥备份路径，并且不会拉起 `node-daemon`。
2. **激活成功依赖外部监管。** 网页激活写完 `etc/node_identity.json` 等文件后主动退出。`start.py` 只是开发辅助，不注册开机服务。正式监管散落在 systemd、launchd、Windows 计划任务和安装脚本里，而且和源码启动会抢同一组端口。
3. **Agent 和应用依赖容器。** App、Agent、HostScript 走 AppLoader，使用 OCI 镜像。macOS/Linux 用 Docker；Windows 在找到 `wslc.exe` 时优先用 WSL containers。上游写明：完整 Windows 安装、Zone 激活和 Jarvis 对话还没有端到端验证。没有容器运行时，内核服务仍可能起来，Jarvis 起不来。
4. **安装根和权限不统一。** 类 Unix 默认 `/opt/buckyos`。Windows 源码启动默认 `%APPDATA%\buckyos`，安装包默认目标是 `C:\BuckyOS\`。桌面产品必须选定一个根，并让当前用户能写它。
5. **路径模型是 Zone 文件系统，桌面是特例。** 单机桌面不跑 CYFS FUSE，`cyfs://<zone>/` 直接映射到 `$BUCKYOS_ROOT/data/`。和宿主「文档」「桌面」目录的融合靠符号链接，Windows 安装笔记已经指出软链接会改变 `bin/` 布局。
6. **固定端口会和本机软件冲突。** 80/443、2980、3180–3183、3200 是系统保留端口。3180 必须本机可访问，否则 Web SDK 和 CLI 找不到服务。
7. **离线安装包仍是施工说明。** `product/buckyos_desktop_installer/` 记录了 rootfs、预装 pkg、mac/Windows 包的思路和 TODO，不是已完成的安装器规格。
8. **开发身份不能出货。** `start.py --all` 使用写死的 `devtest` / `test.buckyos.io`。websdk 里的 `DEV_TEST_KEYS` 是公开测试密钥，上游明确禁止用于真实激活。

## BuckyDesk 应该拥有的

BuckyDesk 只依赖无界面内核，界面全部自己做。进程名单、调用端口和本机页面约定写在 [非 UI 内核](非ui内核.md)。

它要拥有的是「这台电脑」上的这一段：

- 选定并创建运行根，与开发者的 `/opt/buckyos` 或源码 `start.py` 隔开。
- 安装、升级、卸载事务：覆盖安装保留 `data/home`、`data/srv`、`storage`；卸载前讲清哪些会留下。
- 监管上一篇列出的内核进程：开机启动、崩溃拉起、日志入口。
- 一次默认的本机首次激活，让用户不先选择网关拓扑。身份写入 `etc/`，不打开 3182 向导页。
- `bucky desk open` 在 `127.0.0.1:1016` 提供用 gd5 写的页面，监听成功后用浏览器打开这个地址。`bucky cloud serve` 在云主机上只做公网入口。没有公网地址的桌面用 `bucky desk entrance start` 向外连，访问再转回那台桌面。自己有固定公网地址的桌面不经过这台云主机。这一版入口是 HTTP。ZoneGateway 留到内核接上之后。

## 建议的首版范围

首版按「一台电脑、一个用户、一个 OOD、先本机后远程」来切。

- 身份使用本地 `provision` 的落盘结果：单 OOD、无 SN、无 BNS。域名可以使用本机专用名字，只要 `node-daemon` 能读 `etc/.zone.json` 完成本地 boot。这一点要在对接时用当前 `node-daemon` 验证。
- 浏览器只打开 `http://127.0.0.1:1016`。不打开 `control-panel` 的页面，不安装 BuckyOSApp。
- 首版不依赖 frame 服务和 Jarvis，因此也不把 Docker/WSL 当成安装门槛。
- 远程访问、多 OOD、加入已有 Zone，都不放进首版。

仍要产品拍板的选择写在 [05-buckydesk-边界](05-buckydesk-边界.md)。

# 运行、安装与激活

本章记录把 BuckyOS 放进一台桌面电脑时会碰到的运行事实。来源是 `doc/path_usage.md`、`doc/port_usage.md`、`doc/arch/02_boot_and_activation.md`、`doc/arch/11_env_contract.md`、`doc/windows_wslc.md`、`src/start.py`、`src/bucky_project.yaml`、`product/node_active/`、`product/buckyos_desktop_installer/`，以及 `buckyos-pack-installer` 的 readme。

## 运行根

`BUCKYOS_ROOT` 是主机上的运行根。生产安装之后应保持稳定，派生路径都挂在它下面。

| 平台 | 源码启动默认值 | 安装包默认目标 |
| --- | --- | --- |
| macOS / Linux | `/opt/buckyos` | 服务组件同样是 `/opt/buckyos/` |
| Windows | `%APPDATA%\buckyos` | `C:\BuckyOS\` |

环境变量优先于默认值。Windows 上还有工具会再回退到 `%USERPROFILE%\buckyos`。这三处不一致，桌面安装器必须选一个并写入监管进程的环境，不能依赖每个二进制自己的回退。

根目录里和产品行为有关的部分：

| 路径 | 内容 | 覆盖安装 | 卸载 |
| --- | --- | --- | --- |
| `bin/` | 服务二进制、激活页、控制面板 Web、`buckyos` CLI | 覆盖 | 删除 |
| `libexec/buckyos-tool/` | SDK/CLI 与捆绑的 Deno | 覆盖 | 随二进制删除 |
| `etc/` | `node_identity.json`、`start_config.json`、网关配置、scheduler 模板 | 逐文件定义；身份文件来自激活 | 删除前先做身份备份 |
| `data/home/` | 用户数据。桌面不跑 FUSE 时，`cyfs://<zone>/home/...` 落在这里 | 保留 | 保留 |
| `data/srv/` | 服务持久数据和 Zone 共享库 | 保留 | 保留 |
| `data/var/`、`data/cache/` | 运行数据和缓存 | 视安装模式 | 删除 |
| `storage/` | chunk、named store 等内核存储 | 保留 | 保留 |
| `local/` | 本机服务状态 | 可重建 | 删除 |
| `security/` | 设备私钥等 | 保留到卸载策略执行 | 卸载时删除（备份流程另计） |
| `logs/` | 日志 | — | 删除 |

`bucky_project.yaml` 把安装分成 `update`（目标已存在则保留 `data_paths`）和 `install`（先清理再装）。用户数据的保留规则在 `doc/path_usage.md` 写得更细：卸载不删除 `data/home`、`data/srv`、`storage`。软重置会重装服务、删应用数据，同时保留拓扑、分布式存储和用户数据；执行细节文档写的是「待定」。

单机桌面的额外约定：

- 不运行 CYFS FUSE，本 Zone 的 `cyfs://` 映射到 `$BUCKYOS_ROOT/data/`。
- 与宿主用户目录融合靠链接，例如把 `data/home/<user>/Documents` 链到 `C:\Users\alice\Documents`。
- Windows 安装笔记写明：软链接不可用时，`bin/` 的目录结构要改。

容器里的 App 还能看到两块不属于用户 home 的卷：`/opt/buckyos/instance`（本实例可写）和 `/opt/buckyos/tools`（节点共享只读工具）。宿主上的用户数据仍在 `$BUCKYOS_ROOT/data/home/<user>/.local/share/<appid>`。

## 端口

这些端口被占用时，系统会异常。桌面安装前要检测，并决定是改提示、申请防火墙例外，还是失败并说明哪个程序占用了端口。

| 端口 | 用途 | 桌面上的暴露 |
| --- | --- | --- |
| 80 / 443 | ZoneGateway | 只在需要浏览器直接访问 Zone 主机名时才需要 |
| 2980 | RTCP | 远程节点互联才需要公网或局域网可达 |
| 3180 | NodeGateway | 本机必须可访问 |
| 3181 | node-daemon 的 kevent HTTP | 仅本机 |
| 3182 | 激活向导 | 激活期间局域网可达；激活完成后不应继续对外 |
| 3183 | kevent native | 仅本机。Windows 上共享内存路径必须全进程一致，否则事件总线会裂开 |
| 3200 | system-config | 文档写「仅局域网」 |
| 3300 / 3380 / 3400 | verify-hub、task-manager、scheduler | 内核服务，经 kapi 访问 |
| 4000–4130 | repo、控制面板、消息、OpenDAN、文件、HomeStation 等 | 框架服务的固定分配 |
| 10000 起 | 应用实例 | 动态，按应用索引偏移 |

完整表在 `doc/port_usage.md`。应用端口是动态的；上面列出的系统端口才是安装器要预留的。

## 进程怎么被拉起

开发者路径是 `buckyos/src/start.py`：

1. 停掉已知进程。
2. 把 `src/rootfs` 更新到 `BUCKYOS_ROOT`。
3. 后台启动 `node_daemon --enable_active`。

它不注册开机服务。机器上若已有 systemd、launchd 或 Windows 保活任务，必须先用那个服务管理器停掉，否则 `stop.py` 杀进程后会被自动拉起。README 要求源码开发和 BuckyOS Desktop 测试使用不同环境，避免抢运行根、服务和端口。

`node_daemon` 每次启动都尝试读取 `etc/node_identity.json`：

- 读不到，并且带了 `--enable_active`：在 3182 提供激活页和 `/kapi/active`。
- 读不到，并且没带这个参数：打印警告后退出。是否进入激活由安装器或监管进程决定。
- 读到了：走正常 boot。若 `system-config` 里还没有 `boot/config`，反复尝试 `scheduler --boot`。

网页激活成功后，服务端写完身份文件，大约 2 秒后退出进程。没有进程内切换到正常态。监管进程必须发现退出并重新启动 `node-daemon`（此时不再需要激活端口）。BuckyDesk 的进程监管要把这个退出当成成功信号，而不是崩溃。

## 三条激活路径

三条路径都是「给一台还没有身份的安装根写入 Zone / Owner / Device」。它们互不替代，也不能同时写同一套 `etc/`。

### 1. 网页向导

实现：`src/kernel/node_active/` 加 `node_daemon` 的 `active_server.rs`。产品现状说明在 `product/node_active/Node_Active_现状说明_草稿.md`，那份文档声明自己是代码快照，不是 PRD。

- 浏览器打开 `http://127.0.0.1:3182`。
- 向导自动探测运行环境。普通浏览器走网页路线；只有宿主注入了 `window.BuckyApi` 且能读到当前钱包用户时才走钱包路线。
- 网页路线会在设备上生成设备密钥，在浏览器状态里生成 Owner 密钥，提交时把 Owner 私钥发给本机服务端签名。服务端不落盘 Owner 私钥。Review 页会明文展示 Owner 私钥，要求用户自己备份。
- 默认 Zone 名是 `<sn 用户名>.web3.buckyos.ai`。网关要选 SN 中转、端口转发或固定公网 IP。除「WAN + 自有域名」外都需要 SN access token。
- 当前向导把 OOD 列表写成 `["ood1"]`，没有「加入已有 Zone」或恢复备份。
- BNS 文档发布需要 `bns_evm_private_key`。向导没有收集这个字段的步骤，网页用户目前走不到链上发布。

这条路径面向「有 SN 账号、准备让 Zone 被外部解析」的设备。把它原样放进桌面首次启动，用户会先遇到邀请码、网关类型和私钥备份，然后进程退出。

### 2. 钱包向导

同一套向导的另一条分支，由 BuckyOSApp 提供宿主桥。Owner 私钥留在壳里，服务端只收到签好的 JWT。管理员密码哈希必须由钱包响应带上。

BuckyOSApp 的现行需求（`doc/当前需求文档.md`）写明：它可以扫描局域网，也可以让用户手动输入远程 OOD 地址并打开 3182 激活页；已绑定后可以解绑 zone 配置。激活完成后的整套本地配置写回、OOD 进程生命周期、应用安装都不在它的范围内。EVM 交易签名不在现有 `signJsonWithActiveDid` 里，钱包路线的 BNS 发布仍是缺口。

### 3. 本机 provision

实现在 websdk：`buckyos provision status|check|activate`，生产 API 是 `inspectActivationRoot`、`checkOfflineActivation`、`activateOfflineZone`。规格见 websdk `doc/modules/provision.md`。

- 目标是已经有 `bin/` 和 `etc/` 的安装根。
- 单 OOD、`did:web:<domain>`、无 SN、无 BNS、无网络。
- Owner DID 与 Zone DID 都是 `did:web:<domain>`，设备 DID 是 `did:web:ood1.<domain>`。
- Owner 私钥写到调用方指定的已存在目录，权限尽量收成仅所有者可读。Windows 上只做独占创建，不设置 ACL。
- 最后写入 `etc/node_identity.json`。本地 boot 旁路文件是 `etc/.zone.json`。
- 成功结果的 `startup_required=true`。命令本身不启动 Zone，也不访问 3182。
- 与网页激活没有共享锁。部署方必须保证 `node-daemon` 当时没在跑激活服务。
- 不支持二次激活、加入已有 Zone、多 OOD、NAT 拓扑、自动 DNS/TLS。
- `buckyos/src/active.ts` 尚未切换到这套 API，属于上游自己的后续同步项。

对「装完就能在本机用」来说，这是三条里唯一不依赖 SN 的现成实现。它仍要求一个域名和一次明确的密钥备份。`did:web` 这个名字会让人以为必须有公网 DNS；provision 文档说 `configured` 不包含 DNS、TLS 或外部可发现性，本地 boot 靠 `etc/.zone.json`。BuckyDesk 在采用它之前，要用当前 `node-daemon` 做一次「任意本地域名 + 本地 override → scheduler boot 成功」的验证。

开发用的 `start.py --reinstall dev` 会写入 `devtest` / `test.buckyos.io` 的预置身份，跳过向导。那是 DV 环境。websdk 的 `DEV_TEST_KEYS` 使用固定开发助记词，禁止用于真实激活。

## 容器

AppLoader 统一拉起 App、Agent 和 HostScript，包描述仍是 Docker/OCI 镜像。

- Linux 和 macOS 默认 Docker。macOS 安装脚本用 `docker info` 判断可用性，允许 CLI 连到远程引擎；这是为了他们的打包机没有嵌套虚拟化，不等于最终用户可以没有本地引擎。
- Windows 找到 `wslc.exe` 时优先 WSL containers，否则用 Docker。需要 Windows 11 和硬件虚拟化。WSL 文档给出的最低版本是 2.9.3，上游验证用的是 3.0.3.0。
- 可用 `BUCKYOS_CONTAINER_RUNTIME=wslc|docker` 强制选择。两个运行时的镜像和卷不共享，切换前要先停干净。
- 容器访问 Windows 宿主用 `host.wslc.internal`。官方 `paios` 镜像基于 Ubuntu 24.04。Alpine/musl 在当时的 WSLC 上解析这个名字会失败。
- 上游验证覆盖了容器生命周期、卷和重启后读回卷，并写明尚未做完整 Windows 安装、Zone 激活和 Jarvis 对话的端到端验证。

内核里的 Rust 服务是本机进程。没有容器时，Zone 仍可能完成 boot 并打开一部分系统页；Jarvis、脚本型和镜像型应用不会起来。开箱即用要把容器运行时算进安装，而不是写进排错文档。

## 现有安装包

打包入口是 buckyos 根目录的 `make_local_pkg.py`，平台脚本在子模块 `src/publish`（仓库 `buckyos-pack-installer`）。它读取 `src/bucky_project.yaml`，并会构建同级的 `cyfs-gateway` 和 `BuckyOSApp`。

`publish` 段把桌面拆成可选组件：

| 平台 | 组件 | 默认落点 |
| --- | --- | --- |
| macOS | `BuckyOSApp`（已打好的 app bundle） | `/Applications/BuckyOS.app` |
| macOS | `buckyos`，显示名 BuckyOS Desktop Service | `/opt/buckyos/` |
| Windows | `BuckyOSApp` | 用户可选，配置示例是 `C:\BuckyOS\BuckyOSApp` |
| Windows | `buckyos`，系统服务，显示名 BuckyOS Desktop Service | 用户可选，配置示例是 `C:\BuckyOS\` |
| Linux | 只有 BuckyOS Service，`system_service: true` | `/opt/buckyos/` |

Linux 包面向服务器和开发环境。macOS/Windows 才带桌面 App。两个组件都是 `optional`，默认选中。只装 App、不装服务，在 BuckyOSApp 自己的目录笔记里被描述成「系统只剩下 `$BUCKYOS_ROOT/local/`」。那是另一套尚未落地的本机 pkg 设想（`local/bin`、`app-daemon`），当前 Tauri 应用的需求范围没有实现它。

`product/buckyos_desktop_installer/` 里的三份笔记是离线包和安装后目录的思考，包含未完成的 STEP。不要把它们当成现行安装器行为。现行行为以 `bucky_project.yaml` 和 pack-installer 脚本为准。

版本号规则：`src/VERSION` 的内容加上 `buildYYMMDD`。

## 开发者构建链（BuckyDesk 不应暴露）

从源码跑起来需要：Rust、C/C++ 工具链、Python 3.12+、`uv`、Node.js、npm、pnpm、Deno，以及容器运行时。CI 使用 Node 24、pnpm 10.13.1、Deno 2.9.2。还要克隆 `cyfs-gateway`；改 SDK 时再克隆 `buckyos-websdk`。

发布构建可以改为消费一份已经校验过的 npm tarball、SBOM、release manifest 和固定 Deno，而不是在用户机器上编译。BuckyDesk 的安装包应该站在这条发布链的消费端：拿到按平台打好的 rootfs 和网关，再完成本机监管和首次激活。
